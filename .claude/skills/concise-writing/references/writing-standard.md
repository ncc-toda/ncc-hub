# 文章作成基準

AI が作成、修正、レビューする日本語と英語の文章に共通で適用する。
数値は短い文章を優先するための初期値であり、超過は見直しの目安とする。
外部標準の保証値や日英の換算値ではなく、合否の絶対条件にもしない。

## 文と段落

| 項目 | 日本語 | 英語 |
| --- | --- | --- |
| 1 文 | 50 字以下 | 20 語以下 |
| 1 文の読点 | 「、」2 個まで | カンマ数の一律制限なし |
| 1 段落 | 150 字以下 | 60 語以下 |
| 1 段落の文数 | 3 文程度 | 3 文程度 |

- 文や段落に下限は設けない。
- 1 文では主要な主張を 1 つにする。
- 1 段落では 1 つの主題を扱う。
- 超過したら、意味の切れ目で分割するか、不要な語を削る。
- 読点を削るだけの修正はしない。条件や否定を失う短縮もしない。
- 制限回避だけを目的とした改行やリスト化を避ける。

## 意味と語彙

- 結論や必要な行動を先に書く。不要な前置きや賛辞を削る。
- 主体と指示語の参照先を明確にする。条件は対象の処理に近づける。
- 事実と推測を区別する。未確認事項を断定しない。
- 要件、互換性、リスク、再現手順などの必要情報を保つ。
- 同じ概念には同じ用語を使う。既存文書の文体を尊重する。
- 詳細の正本は各言語内で 1 つにする。判断に必要な要約や日英対訳は許容し、意味のない結論の再掲は削る。
- 語彙のブラックリストや AI 文体の判定器は使わない。

英語の一般語は A2〜B1 程度を目安にする。
正確さに必要な B2 語や専門用語は許容する。
文化依存の比喩や慣用句は避ける。

日本語は一般的で具体的な語彙を優先する。
不要なカタカナ語や難解な漢語は見直す。
語彙レベルや品詞数による機械判定は行わない。

## 表記

- 日本語と英数字の間には半角スペースを入れる。数字と助数詞の間も同様にする（例: `3 つ`、`1 文`）。
- インラインコードと日本語の間にも半角スペースを入れる。直後に句読点や括弧が続く場合は入れない。
- 全角括弧の内外には空白を入れない。半角括弧は外側に空白を入れ、内側には入れない。
- 文頭、文末、句読点の前後には不要な空白を足さない。
- `#9`、`100%`、`v1.0.0` の内部は分割しない。
- URL やコード内部には空白規則を適用しない。これらを網羅する独自検査は作らない。

表記の例を示す。

- GitHub の Issue を更新する
- ツール (tool) を使う
- 設定（任意）を読む

## 構造と改行

- 静的な Markdown は原則として 1 文 1 行にする。同じ主題の文は同じ段落にまとめ、段落は空行で区切る。
- Issue、PR、コメント、回答は段落内で改行せず、連続して記述する。GitHub は単一改行を改行として表示する。
- 表示先の改行仕様に合わせて自然な表示を確認する。チャットの表示仕様を GitHub と同一視しない。
- 行末 2 スペースの強制改行は使わない。
- 見出しは内容を予測できる名前にする。並列情報は箇条書きにし、手順には番号を使う。
- リスト内の粒度と文法を揃える。
- 見出し長や項目数の一律制限は設けない。深い階層や長い列挙は必要性を見直す。長い回答では見出しの使用も認める。

## 用途ごとの補足

### AI 向け指示文書

- 一意に解釈できる形にする。重要な指示を前方に置き、不要な重複を削る。
- 条件と処理の対応を保つ。
- 読み込み方は文書の種類によって異なる。全ファイルが常時全文読み込まれるとは扱わない。
- 行数制限や参照階層の専用検査は追加しない。

### Issue、PR、レビューコメント

- 先頭段落に結論を書く。テンプレートの見出しは変えない。
- レビューへの返信は対応内容と未対応の理由だけを書く。

### ユーザーへの回答

- 結論、根拠、次の行動の順に書く。定型の報告書式は使わない。
- 承認依頼、失敗、未完了、破壊的操作の予告は必ず明示する。
- 将来の変更で参照する設計判断は、必要に応じて ADR または設計文書へ残す。

### 既存文書と長文

- 既存テンプレートや必要な長文は文脈を優先する。
- 正確さを損なう場合は数値超過を許容する。例外の台帳や承認フローは新設しない。
- 既存文書は変更箇所だけを直し、一括改稿はしない。

## 機械検査との対応

`check-prose.sh` は次の項目だけを検査する。

| 項目 | ルール | 補足 |
| --- | --- | --- |
| 日本語の文長 | `sentence-length` | 漢字、ひらがな、カタカナを含まない文は数えない |
| 日本語の読点数 | `max-ten` | 名詞の列挙の読点は数えない |
| 英語の文長 | `en-max-word-count` | 語数で数える |
| 日英間とインラインコードの空白 | `preset-ja-spacing` の一部 | 全角括弧と全角文字間の空白も見る |

次は検査しないため、推敲時に確認する。

- 段落の長さと文数、見出し、構造、重複、総量
- 半角括弧の外側の空白
- 語彙と意味

既存ルールの仕様による差もある。

- インラインコードの文字数は文長に含まれる。
- 引用と、リンクだけの段落は文長を数えない。
- 見出しと表のセルは文長を数えない。空白の規則は対象になる。
- 半角の `[]` は全角括弧と同じ扱いになる。
- 警告はすべて `warning` で、終了コードは 0 になる。

## 例

長い文は意味の切れ目で分ける。

```text
修正前: 設定ファイルを編集したあとに、必ずビルドを実行して、その結果を確認してから、変更を反映する。
修正後: 設定ファイルを編集したら、ビルドを実行して結果を確認する。問題がなければ変更を反映する。
```

Issue や PR では段落内で改行しない。

```text
1 文目。2 文目。3 文目。

次の段落。
```

空白は英数字とインラインコードの前後に入れる。

```text
修正前: GitHubのIssueを`gh`で更新する。
修正後: GitHub の Issue を `gh` で更新する。
```
